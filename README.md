# Alex Studio — سجل القرارات المعتمدة (النسخة 3 — النهائية)

> **حالة الوثيقة:** مسودة نهائية للمراجعة والاعتماد.  
> **ما تغيّر في هذه النسخة:**  
> - تمت إضافة 5 تعديلات (Rate Limiting، معالجة الأخطاء، نسخ احتياطي، اختبار الأداء، صياغة Code Untrusted).  
> - تحديث "المرحلة 0 — إثبات المفهوم" (5 خطوات) لتصبح أكثر تحديداً وقابلة للاختبار.  
> - توحيد المصطلحات (Code Untrusted، Rate Limiting، Error Handling).

---

## 1. هدف المشروع

إنشاء استوديو تطوير مدعوم بالذكاء الاصطناعي للاستخدام الشخصي في إدارة مشاريعي وبنائها ومراجعتها وتطويرها، وليس كخدمة تجارية عامة. يهدف إلى تسريع التطوير مع الاحتفاظ بالتحكم الكامل للمستخدم.

**المبدأ الأساسي:** الذكاء الاصطناعي يقترح؛ صاحب المشروع يراجع ويقرر وحده.

## 2. طريقة التشغيل

- **واجهة متجاوبة:** متوافقة مع هاتف سامسونغ والكمبيوتر.
- **الوصول المتعدد:** البنية تسمح بالوصول من أجهزة مختلفة مستقبلاً، لكن لن يُفعّل الوصول عن بُعد إلا بعد تطبيق آلية مصادقة آمنة ومختبرة.
- **الأمان أولاً:** حماية المشاريع والملفات ومفاتيح API أولوية مطلقة.
- **الاستخدام المحلي كقاعدة:** في هذه المرحلة، التشغيل على الجهاز المحلي فقط (localhost).
- **مؤكد:** لا وصول عن بُعد في النسخة الأولى.

## 3. دعم أنواع المشاريع

- **البداية:** نوع مشروع واحد فقط — HTML/CSS/JS ثابت (القرار 3 في البند 7).
- **السبب:** أبسط نوع ممكن، لا يحتاج build، لا يحتاج Node، لا يحتاج تثبيت حزم، ويعاين داخل iframe معزول بـ CSP صارمة.
- **التوسع:** تصميم البنية بحيث تُضاف أنواع أخرى (React + Vite، ثم ما يلزم) لاحقاً دون إعادة بناء النظام.
- **الأولوية:** إثبات دورة إدارة الملفات → الاقتراح → المراجعة → الموافقة → المعاينة → الفحص على هذا النوع البسيط أولاً.

## 4. التحكم بالتعديلات والأمان

- **مبدأ الاقتراح لا التنفيذ:** الذكاء الاصطناعي يقترح؛ المستخدم يراجع ويقرر.
- **شفافية كاملة:** عرض الملفات والتغييرات المقترحة مع **Diff واضح** قبل التطبيق.
- **موافقة صريحة إلزامية:** لا يُطبّق أي تعديل دون ضغط زر اعتماد صريح.
- **عزل الملفات:** جميع عمليات القراءة/الكتابة مقيدة داخل نطاق مجلد المشروع (`workspace/`)؛ منع أي وصول خارج النطاق.
- **التحقق من المسارات:** رفض أي مسار مطلق، أو يحتوي `..`، أو يخرج عن `workspace/` بعد `realpath`.
- **ضوابط العمليات الحساسة:** العمليات التي تؤثر على النظام (تثبيت حزم، تشغيل أوامر) تتطلب عرضاً صريحاً للموافقة قبل التنفيذ.
- **حماية المفاتيح:** مفاتيح API في الخادم الخلفي فقط (`.env.local`)، لا تُكشف للمتصفح، ولا تدخل ملفات المشروع، ولا تُصدَّر في ZIP.
- **الكود المولَّد غير موثوق في جميع المراحل:** يُعامل كاقتراح **غير موثوق** في جميع المراحل؛ حتى بعد الاعتماد، المعاينة والفحوص تتم داخل بيئة معزولة. لا يُنفَّذ الكود على المضيف.
- **الأسرار لا تدخل بيئة المعاينة:** حتى لو كانت البيئة معزولة.
- **الفحوص تُشغَّل داخل نفس بيئة العزل:** لا على المضيف مباشرة.
- **توثيق دقيق للفحوص:** تسجيل ما نُفذ وما لم يُنفذ؛ نجاح فحص واحد لا يعني جاهزية كاملة.
- **Rate Limiting:** وضع حد أقصى لعدد طلبات API في الدقيقة/الساعة لمنع استنزاف التكلفة بالخطأ.
- **استراتيجية معالجة الأخطاء:** معالجة أخطاء API، أخطاء الملفات، وانهيار preview مع رسائل واضحة للمستخدم.
- **نسخ احتياطي:** نسخ احتياطي دوري (ZIP) للمشروع completo، أو Git remote اختياري (بمصادقة).

## 4.1 دورة العمل الإلزامية للذكاء الاصطناعي

دورة العمل المطلوبة داخل Alex Studio هي:

**فهم ← تخطيط ← تنفيذ ← اختبار ← تشخيص ← إصلاح ← إعادة اختبار ← تسليم موثّق.**

ويجب أن يعمل المساعد كوكيل تطوير يتبع هذه الدورة، لا كمولّد نصوص أو اقتراحات منفصلة فقط:

1. **الفهم:** تحليل طلب المستخدم وسياق المشروع وملفاته ذات الصلة، وتحديد الهدف والقيود وأي معلومات ناقصة.
2. **التخطيط:** إعداد خطة تنفيذ قصيرة تحدد الملفات المتأثرة، والتغييرات المتوقعة، والفحوص المناسبة قبل تعديل الملفات.
3. **التنفيذ:** إنشاء التغييرات البرمجية الفعلية على ملفات المشروع داخل مساحة العمل المعزولة، مع إبقاء التغييرات المقترحة قابلة للمراجعة وعدم تجاوز موافقة المستخدم الصريحة قبل تطبيقها.
4. **الاختبار:** تشغيل الفحوص المتاحة والملائمة لنوع المشروع، مثل فحص الأنواع والتنسيق والاختبارات والبناء واختبارات المتصفح عند توفرها.
5. **التشخيص:** عند الفشل، جمع مخرجات الفحص وتحديد السبب المرجح بدليل من الخطأ، لا التخمين أو إخفاء الفشل.
6. **الإصلاح:** تعديل السبب المحدد ضمن نطاق المهمة، مع المحافظة على التغييرات السابقة والقيود الأمنية.
7. **إعادة الاختبار:** إعادة الفحوص التي فشلت، ثم الفحوص المرتبطة بالتغييرات؛ ولا يُعلن النجاح إلا بناءً على نتيجة فعلية للنسخة المختبرة.
8. **التسليم الموثّق:** عرض ملخص التغييرات والملفات المتأثرة ونتائج الفحوص الفعلية والفحوص غير المنفذة وأي مخاطر أو عمل متبقٍ.

### ضوابط حلقة الإصلاح

- تُكرر دورة التشخيص والإصلاح وإعادة الاختبار حتى تنجح الفحوص المطلوبة أو يظهر مانع واضح، مع حدّ محاولات قابل للضبط لمنع التكرار غير المنتهي.
- إذا تعذر إصلاح الفشل أو تشغيل فحص، يجب إظهار السبب والنتيجة المتبقية بوضوح؛ لا يجوز الادعاء بأن المهمة نجحت.
- يجب أن تكون كل محاولة إصلاح مرتبطة برسالة خطأ أو نتيجة اختبار قابلة للفحص، لا بتغييرات عشوائية.
- تُعامل مخرجات النموذج والكود المقترح على أنها غير موثوقة، وتبقى ضوابط عزل الملفات والبيئة والأسرار وموافقة المستخدم نافذة طوال الدورة.
- لا تُطبّق تغييرات الملفات بصمت. يجب عرض Diff واضح والحصول على موافقة صريحة قبل الكتابة؛ ولا يعني نجاح الاختبارات موافقة تلقائية على الدمج.
- يُسجّل التقرير النهائي معرّف النسخة أو commit الذي جرى اختباره، وأسماء الأوامر أو الفحوص ونتائجها، وأي فحوص تخطّتها البيئة.

## 5. ترتيب التنفيذ المعتمد

1. **الأساسيات والأمان:** تأسيس المشاريع والملفات، نظام الحفظ وإعادة الفتح، **عزل الملفات وحماية المفاتيح**.
2. **المساعدة الذكية:** تحويل الطلبات إلى خطط عمل واضحة واقتراحات تعديل.
3. **المراجعة والموافقة:** عرض Diff، زر اعتماد/رفض، تطبيق ذرّي بعد الموافقة فقط.
4. **المعاينة والفحص المعزول:** معاينة HTML ثابت داخل iframe معزول بـ CSP صارمة، مع عرض نتائج الفحص الفعلية.
5. **الإكمال والتوثيق:** تصدير ZIP، سجل الدفعات المعتمدة، التراجع عن آخر دفعة.

> هذا الترتيب **معتمد كمسار تنفيذي**، وليس دليلاً على إنجاز أي مرحلة. يجب إكمال كل مرحلة واختبارها قبل الانتقال للتالية.

## 6. شروط اعتماد النسخة الأولى (معايير القبول)

يجب استيفاء جميع ما يلي لاعتبار النسخة الأولى جاهزة:

- [ ] **إدارة المشاريع:** إنشاء مشروع، حفظه، وإعادة فتحه بنجاح وبشكل كامل.
- [ ] **عرض التعديلات:** عرض خطة التعديلات والملفات المتأثرة قبل التطبيق.
- [ ] **دورة الذكاء الاصطناعي الكاملة:** إثبات عملي لمسار الفهم والتخطيط والتنفيذ والاختبار والتشخيص والإصلاح وإعادة الاختبار والتسليم الموثّق، مع إظهار نتائج الفحوص الفعلية.
- [ ] **حلقة إصلاح منضبطة:** عند فشل اختبار، يظهر السبب من مخرجاته، ويُنفذ إصلاح مرتبط به، ثم يعاد الاختبار؛ وعند تعذر النجاح تُعرض الحالة المتبقية دون ادعاء النجاح.
- [ ] **الموافقة/الرفض:** إمكانية قبول التغييرات أو رفضها، مع تطبيقها فقط عند الموافقة الصريحة.
- [ ] **ضمان عدم التطبيق الصامت:** إثبات عملياً عدم تطبيق أي تعديل دون موافقة (فحص checksum قبل/بعد الرفض).
- [ ] **عزل الملفات:** إثبات منع الوصول إلى الملفات خارج نطاق المشروع (اختبار Path Traversal).
- [ ] **الفحص:** تشغيل الفحص المتاح وعرض نتائجه الفعلية مع توضيح الحدود.
- [ ] **المعاينة الآمنة:** معاينة المشروع ضمن حدود أمان واضحة (iframe معزول + CSP).
- [ ] **تصدير ZIP:** تصدير المشروع كأرشيف، مع استثناء `.git/` و`.alex/` و`.env*` و`node_modules/`.
- [ ] **سجل التعديلات والتراجع:** سجل الدفعات المعتمدة + زر «تراجع عن آخر دفعة».
- [ ] **حماية المفاتيح:** التأكد من عدم كشف مفاتيح API في الواجهة أو الملفات المصدرة.
- [ ] **عداد التكلفة:** عرض مجموع التوكنات والتكلفة التقديرية لكل مشروع ولكل شهر.
- [ ] **تحذير الحد الشهري:** تنبيه عند بلوغ الحد الشهري المقترح (تحذير فقط، لا إيقاف تلقائي في هذه المرحلة).
- [ ] **اختبار الأداء الأساسي:** وقت استجابة API < 10s، تحميل الملفات < 2s.

## 7. القرارات المحسومة (كانت معلّقة في النسخة السابقة)

**ملاحظة:** هذه قرارات مقترحة بناءً على تحليل تفصيلي في المراجعة السابقة. تصبح «معتمدة» بتوقيعك عليها. إن أردت تعديل أي منها، يُعدَّل قبل البدء.

### القرار 1 — سجل التعديلات والتراجع: نعم، بأبسط صورة
- **داخل النسخة الأولى:** سجل يعرض قائمة «دفعات معتمدة» (كل ضغط «اعتماد» = دفعة واحدة). زر «تراجع عن آخر دفعة» فقط.
- **خارج النسخة الأولى:** تراجع انتقائي، فروع، دمج، سجل متعدد المستويات.
- **الآلية:** Git محلي لكل مشروع. كل اعتماد = commit. التراجع = revert لآخر commit. الواجهة تُجرِّد Git.
- **لماذا:** يحقق شرط البند 6 بأقل تعقيد ممكن.

### القرار 2 — تصدير ZIP: نعم
- **زر واحد،** ينتج `project-name.zip` يحتوي ملفات المشروع + README إن وُجد.
- **استثناءات إلزامية:** `.git/`، `.alex/`، `.env*`، `node_modules/`.
- **لماذا:** بسيط، عالي القيمة، ويمنع تسريب الأسرار أو التاريخ.

### القرار 3 — نوع المشروع الأول: HTML/CSS/JS ثابت
- **مشروع ثابت،** لا build، لا Node، لا تثبيت حزم.
- **المعاينة** داخل iframe معزول بـ CSP صارمة (لا يحتاج WebContainers لهذا النوع).
- **التوسع لاحقاً:** React + Vite في مرحلة تالية بعد إثبات النظام كاملاً.
- **لماذا:** يبسّط المعاينة، العزل، الفحص، وإدارة التبعيات — ويثبت صحة الدورة قبل إضافة تعقيد.

### القرار 4 — التخزين والوصول: محلي فقط في النسخة الأولى
- **ملفات على القرص + Git** لكل مشروع.
- **لا قاعدة بيانات،** لا سحابة، لا مصادقة متعددة المستخدمين.
- **الواجهة تصمم بطبقة وصول** قابلة للاستبدال لاحقاً بمصادقة دون إعادة كتابة.
- **الوصول عن بُعد مؤجل** حتى يوجد مصادقة حقيقية مختبرة (يتسق مع البند 2).
- **لماذا:** يقلل التعقيد والمخاطر، ويحقق «الأمان أولاً» بأبسط شكل.

### القرار 5 — حدود التكلفة: حد شهري بسيط + عداد
- **حد شهري مقترح:** 5 دولارات (قابل للتعديل).
- **عداد بسيط:** صفحة واحدة تعرض مجموع التوكنات والتكلفة التقديرية لكل مشروع ولكل شهر.
- **عند بلوغ الحد:** تحذير فقط، لا إيقاف تلقائي في النسخة الأولى.
- **خارج النسخة الأولى:** حدود يومية، تقدير تكلفة مسبق، تحذيرات متعددة، إيقاف تلقائي.
- **لماذا:** يكفي للتوعية دون بنية إضافية. الفاتورة النهائية تُراقب من لوحة المزوّد.

## 8. حدود هذا السجل

- هذا السجل يثبت **الاتجاه، المبادئ، الترتيب، والقرارات الخمسة.**
- لا يعني أن المواصفات التقنية النهائية مكتملة، ولا أن أي كود نُفّذ أو اختُبر.
- أي قرار جديد يُضاف فوراً مع التاريخ.
- لا يجوز الخروج عن مبادئ **الموافقة الصريحة، عزل الملفات، وحماية المفاتيح** في أي مرحلة.

## 9. الخطوة التالية — Phase 0: إثبات المفهوم (Proof of Concept)

> **الغرض:** إثبات أخطر افتراضين قبل الاستثمار في البناء الكامل.  
> **القاعدة:** كل خطوة تُختبر وتُتحقق قبل الانتقال للتالية. لا تنتقل إلى Phase 1 قبل إكمال جميع 5 خطوات.

### Step 0.1 — scaffold Next.js + TypeScript

- إنشاء مشروع `alex-studio` بـ `create-next-app` مع TypeScript.
- إعداد هيكل المجلدات:
  ```
  alex-studio/
  ├── app/                    # Next.js App Router
  │   ├── api/                # API routes
  │   ├── projects/           # صفحة إدارة المشاريع
  │   ├── editor/             # صفحة التحرير + Diff
  │   └── preview/            # صفحة المعاينة
  ├── lib/                    # utilities (file ops, git, AI)
  ├── components/             # React components
  └── workspace/              # sandbox (gitignored, local only)
  ```
- **اختبار:** `npm run dev` يعمل بدون أخطاء، TypeScript compiles.

### Step 0.2 — DiffEditor (Monaco) بين ملفين

- تثبيت `@monaco-editor/react` و `diff`.
- إنشاء component `DiffEditor` يعرض فروقات بين ملفين (original vs modified).
- **اختبار:** تغيير `src/index.html` و `src/index.modified.html` → Diff يظهر بوضوح (additions/removals).

### Step 0.3 — API route: تغيير ذرّي مع نسخة احتياطية

- إنشاء `/api/files/apply` (POST) يقبل `{ projectId, path, content }`.
- **الآلية:**
  1. التحقق من المسار (reject absolutes, `..`, outside workspace).
  2. نسخة احتياطية → `.alex/backups/{timestamp}.bak`.
  3. كتابة الملف ذرّياً (tmp → rename).
  4. Git commit تلقائي (أو revert عند فشل).
- **اختبار:**
  - تطبيق تغيير → ملف يُحدث + نسخة احتياطية موجودة.
  - محاولة مسار `../../../etc/passwd` → 403 Forbidden.
  - محاولة مسار `/etc/passwd` → 403 Forbidden.

### Step 0.4 — معاينة HTML في iframe معزول (CSP)

- إنشاء `/preview/[projectId]` (route) يعرض ملفات HTML داخل `<iframe sandbox="allow-scripts" srcdoc="...">`.
- **CSP headers:** `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; frame-ancestors 'none'`.
- **اختبار:**
  - معاينة `index.html` بسيط → يعرض correctamente.
  - محاولة `fetch('http://localhost:3000/api/secrets')` من داخل iframe → محظور (CSP).
  - محاولة `window.parent.document` → محظور (sandbox).

### Step 0.5 — اختبار أمان: محاولة الوصول خارج المشروع

- **اختبارات:**
  1. `GET /api/files/read?path=../../../etc/passwd` → 403.
  2. `GET /api/files/read?path=/etc/passwd` → 403.
  3. `POST /api/files/apply` with `path: "../../outside.txt"` → 403.
  4. `POST /api/files/apply` with `path: "workspace/../outside.txt"` → 403.
  5. `GET /api/files/read?path=workspace/../../etc/passwd` → 403.
- **النتيجة المقبولة:** جميع 5 محاولات تُرفض بـ 403. **أي نجاح = فشل Phase 0.**
